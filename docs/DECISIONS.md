# Architecture Decision Records

Short ADRs. Format: context → decision → consequences. Status: Accepted / Superseded.

## ADR-001: Cloud storage and hosting — Accepted (2026-10-27)
**Context:** The brainstorming doc left storage open (cloud vs on-prem vs hybrid).
**Decision:** Cloud (provider and topology in ADR-009). PostgreSQL 16 + PostGIS with daily backups and point-in-time recovery; S3-compatible object storage for CAD files, tiles and photos (MinIO locally); services run as Docker containers.
**Consequences:** No on-prem servers to maintain. Original CAD files are kept read-only in object storage; As-Built versions are separate objects. Internet is needed for the web app; the mobile app works offline and syncs.

## ADR-002: AutoCAD processing on the server only — Accepted (2026-10-27)
**Context:** Open question whether AutoCAD is needed on user machines.
**Decision:** v1 is web + mobile only. DWG/DXF is read and written by the Python worker (ODA File Converter / LibreDWG for DWG→DXF, ezdxf for parsing and As-Built DXF export). No local AutoCAD plugin.
**Consequences:** Users do not need AutoCAD licences to use the platform. Exported As-Built DXF must be verified in AutoCAD/BricsCAD as part of acceptance. A local plugin can be added later behind the same API.

## ADR-003: Technology stack — Accepted (2026-10-27)
**Decision:** As defined in the build plan: pnpm + Turborepo monorepo; NestJS API; Next.js web; Expo React Native mobile with MapLibre + Skia + WatermelonDB; Python 3.12 CAD worker; PostgreSQL/PostGIS; Redis/BullMQ; Martin/PMTiles; GitHub Actions.
**Consequences:** Shared TypeScript contracts across web, mobile and API; Python is limited to the CAD worker.

## ADR-004: Clean architecture + modular monolith — Accepted (2026-10-27)
**Decision:** One NestJS module per bounded context with domain / application / infrastructure / interface layers (see `docs/ARCHITECTURE.md`). Contract-first schemas in `packages/shared`.
**Consequences:** Modules can be developed in parallel by separate agents against fixed contracts, and can be split into services later if needed.

## ADR-005: Agent and model routing — Accepted (2026-10-27)
**Decision:** Hard reasoning (architecture, finance, geometry, sync, security) → Opus; feature implementation and tests → Sonnet; mechanical work (scaffolding, i18n, lint, docs, search) → Haiku. Agents are defined in `.claude/agents/`. Contracts are fixed first so implementation agents can run in parallel worktrees.
**Consequences:** Most tokens are spent on Sonnet/Haiku; Opus is used where a mistake is expensive.

## ADR-006: Drizzle ORM with explicit SQL migrations — Accepted (2026-10-27)
**Decision:** Drizzle for typed queries; migrations are plain SQL files (so PostGIS types, extensions, triggers and constraints are explicit and reviewable).
**Consequences:** No ORM magic around geometry; spatial queries use `sql` templates in repository implementations only.

## ADR-007: Authentication and authorization — Accepted (2026-10-27)
**Decision:** Short-lived JWT access token (15 min, claims: `sub`, `isAdmin`) + opaque refresh token (30 days) stored as SHA-256 hash, rotated on every use; reuse of a rotated token revokes the whole token family. Passwords hashed with argon2id. Authorization = role per project (`assignments`) + optional zone scope; `admin`, `pm`, `qc` are project-wide. Memberships are resolved per request, not baked into the token.
**Consequences:** Revoking access takes effect within one access-token lifetime. Web stores tokens in httpOnly cookies via the Next.js server; mobile stores them in the OS secure store.

## ADR-008: Python worker tooling — Accepted (2026-10-27)
**Decision:** `uv` for dependency management, Python ≥ 3.12, `ruff` + `mypy --strict` + `pytest`.

## ADR-009: Hosting on Hetzner Cloud under ftthtracker.projectflow.site — Accepted (2026-10-27)
**Context:** ADR-001 chose cloud hosting; the provider and domain are now fixed.
**Decision:** Hetzner Cloud. Production on one dedicated-vCPU VPS (e.g. CCX23) and staging on a smaller VPS (e.g. CPX21), both running Docker Compose behind Caddy with automatic Let's Encrypt certificates. Hetzner has no managed PostgreSQL, so PostgreSQL/PostGIS runs in a container on a Hetzner Volume with daily base backups and WAL archiving (WAL-G or pgBackRest) to Hetzner Object Storage, giving point-in-time recovery; a restore is tested monthly. Files, CAD drawings, tiles and photos go to Hetzner Object Storage (S3-compatible), replacing MinIO outside local development. Images are built in GitHub Actions, pushed to GHCR, deployed to staging automatically and to production after manual approval.
Hostnames (A records at the `projectflow.site` registrar):
- `ftthtracker.projectflow.site` — web app
- `api.ftthtracker.projectflow.site` — API (used by web server and mobile app)
- `tiles.ftthtracker.projectflow.site` — vector tiles
- `staging.ftthtracker.projectflow.site` — staging (API and tiles under `api.staging…` / `tiles.staging…`)
**Consequences:** Low monthly cost and EU data location. We operate the database ourselves, so backups, restore drills, monitoring and security updates are our responsibility (scripts and runbook delivered in Phase 7). The code stays provider-neutral: everything is configured by env vars (`DATABASE_URL`, `S3_ENDPOINT`, `CORS_ORIGINS`, …), so moving to a managed database later needs no code change.

## ADR-010: Early staging environment on the shared Hetzner server — Accepted (2026-10-27)
**Context:** The owner wants a reachable environment now, before Phase 1, on the existing Hetzner server `49.13.167.124`, which already runs other apps (invoices, app, n8n) behind a host-level Caddy that imports one snippet per app. The owner has no deploy keys set up and prefers not to manage server secrets.
**Decision:** Pull-based staging that follows the server's conventions.
- `infra/staging/bootstrap.sh` is run once as root from the Hetzner web console (and is safe to re-run). It:
  - creates user `ftth-deploy`, `/srv/ftth`, a clone of the public repo and generated secrets in `/srv/ftth/.env`;
  - renders `/srv/ftth/ftthtracker.caddy` and adds a single `import` to `/etc/caddy/Caddyfile`, with a backup, `caddy validate` and automatic rollback;
  - installs `ftth-autodeploy` and its systemd timer, then deploys and creates the first admin with a random password.
- Every 2 minutes `ftth-autodeploy` compares `origin/main` with the deployed commit. When the matching GHCR images (`<sha>`, published by `publish-images.yml`) exist, it checks the commit out, runs `compose up --wait`, and rolls back to the previous commit on failure.
- The stack (`ftth-staging`) runs its own PostGIS, Redis (password), api, web, cad-worker and a nightly `pg_dump` kept 7 days. Only web and api listen, on loopback ports chosen by bootstrap (3310/3311 by default).
- Martin and MinIO are not deployed until tiles are gated and uploads exist (Phase 1). Staging uses `NODE_ENV=production`, so the dev seed is refused. Login and refresh are rate-limited.
**Consequences:**
- No GitHub secrets, no inbound deploy SSH, no new public ports, and no edits to other apps' config.
- Each merge to `main` reaches staging within a few minutes.
- GHCR packages must be public for anonymous pulls.
- Resources are shared with other apps, so heavy CAD processing may need its own server later.
- Off-site backups, WAL/PITR, monitoring and production remain Phase 7 work.

## ADR-011: Work orders, money and Excel import — Accepted, assumptions pending owner confirmation (2026-10-27)
**Context:** A project has several work orders (أوامر التكليف), each with its own items, quantities, prices and value (brainstorming §4, §7, §8 rules 1–2). Required item fields, duplicate handling and file formats are open questions (§11).
**Decision:**
- Tables `work_orders`, `work_order_items`, `work_order_attachments` (migration 0003, columns in `docs/phase-1a-data-model.md`). Unique `(project_id, number)`; unique line number per order; children reference `(project_id, work_order_id)`.
- Money and quantities: decimal **strings** in the API (`Decimal4StringSchema`: ≥ 0, ≤ 14 integer and ≤ 4 fraction digits), `numeric(18,4)` in PostgreSQL, a bigint-backed `Decimal` value object in the API domain. No `number` arithmetic. Line amount = quantity × unit_price, **exact** (scale 8, `numeric(36,8)` generated column), never rounded in 1a; work-order total = Σ amount computed in the domain and checked against `SUM(amount)` in a DB-level test. Currency is copied from the project when the order is created and is immutable (trigger).
- Entry: manual CRUD; Excel import = stateless preview (detect header row, suggest mapping from Arabic/English/French synonyms, per-row issues) then an atomic commit that re-parses the same file (sha256 must match) and creates one new work order. The xlsx is kept as an `import_source` attachment. PDF attachments are stored, not parsed.
- Every change appends to `events` (types in `packages/shared/src/events/domain-events.ts`). Header edits use optimistic concurrency (`version`).
- Permissions: `packages/shared/src/auth/permissions.ts` (role → permission strings) checked by a permission guard after `ProjectScopeGuard`, and `project_id` in every repository query.
**Assumptions the owner must confirm:**
1. Required item fields are code, description, unit, quantity, unit price. Quantity and price ≥ 0, at most 4 decimals.
2. Duplicate codes in one work order are never merged. In the import they are warnings that block the commit until the user excludes rows or explicitly keeps each code as separate lines; the same explicit acceptance applies to manual entry.
3. Line amounts are kept exact; the rounding rule (and currency decimals) is decided before invoicing (Phase 5). A sheet "amount" column is only cross-checked (warning), never stored.
4. Only the work-order number is required on the header; title, issue date and notes are optional.
5. A work order can be hard-deleted while nothing references its items (the event keeps a full snapshot). From Phase 2 on, references will block deletion.
6. Permissions: admin and pm write; admin, pm, qc and supervisor read (supervisors see prices project-wide, not limited to their zones); contractor has no access yet.
**Consequences:** Clients never parse money as floats. Rounding is an explicit later decision, not an accident of storage. Re-parsing on commit avoids server-side temp state at the cost of uploading the file twice.

## ADR-012: Storage port (fs | s3) and API-mediated uploads — Accepted (2026-10-27)
**Context:** ADR-001/009 store files in S3-compatible storage, but staging has no object storage yet (ADR-010). The roadmap planned presigned uploads; web tokens, however, live in httpOnly cookies behind Next.js route handlers (ADR-007), so the browser cannot sign S3 requests itself, and the worker must read the same files.
**Decision:**
- One `ObjectStorage` port (`apps/api/src/common/object-storage.port.ts`): `put` (streamed, write-once, size-limited, returns size and sha256), `get`, `stat`, `delete`. Adapters: `fs` (a directory volume mounted in both api and cad-worker, used on staging now) and `s3` (Hetzner Object Storage / MinIO later). Selected by `STORAGE_DRIVER=fs|s3`; `STORAGE_FS_ROOT` (default `/var/lib/ftth/storage`); S3 settings are required only for `s3`. The worker gets the same variables.
- Keys are generated, never user-supplied: `projects/<projectId>/cad/<fileId>/original.<dwg|dxf>`, `…/cad/<fileId>/converted.dxf`, `projects/<projectId>/work-orders/<workOrderId>/attachments/<attachmentId>.<pdf|xlsx>`. Original names stay in the DB.
- **Deviation from the roadmap:** in 1a uploads go through the API as streamed multipart (`MAX_UPLOAD_MB`, default 100) — no presigned URLs. The Next.js route handler streams the body through without buffering. Downloads are streamed by the API after the permission check.
- Originals are immutable: write-once keys plus a DB trigger that rejects changes to the original's name, key, size and hash.
**Consequences:** One code path for staging and production; uploads cost API bandwidth and a long-lived request (acceptable at ≤ 100 MB and few users). Presigned uploads can be added later behind the same port for the mobile app (photos) without changing keys. The fs volume must be backed up with the database until s3 is used.

## ADR-013: Redis-list job protocol for the Python CAD worker (not BullMQ) — Accepted (2026-10-27)
**Context:** ADR-003 lists BullMQ, but BullMQ's data layout is a Node implementation detail; the CAD worker is Python (ADR-002/008). We need at-least-once delivery that survives worker crashes, without a second broker.
**Decision:**
- Message: JSON `{id, type:'cad.import', cadFileId, projectId, storageKey, format, attempt, enqueuedAt}` — `CadImportJobSchema` (Zod, `packages/shared`) mirrored by a pydantic model (`workers/cad/cad_worker/adapters/job_message.py`). The Phase 0 `health` job stays.
- Producer (API): in one transaction set `cad_files.status='queued'` and a new `current_job_id`, append the event, commit; then `LPUSH cad:jobs <json>`. If the push fails, mark the file `failed` (`ENQUEUE_FAILED`) so the user can reprocess.
- Consumer: `BLMOVE cad:jobs cad:processing:<workerId> RIGHT LEFT <timeout>` (FIFO). Heartbeat `SET cad:worker:<workerId> … EX 30` every 10 s. Ack = `LREM cad:processing:<workerId> 1 <raw>` **after** the final DB commit. A per-worker in-flight list (instead of one shared `cad:processing`) lets a restarted or second worker recover only the work of dead workers.
- Recovery (on start and every 60 s): for every `cad:processing:*` whose heartbeat key is missing (or is this worker's own list on start), move each item back with a Lua script (atomic `LREM` + `LPUSH` with `attempt + 1`). At `attempt = 3` the file is marked `failed` (`MAX_ATTEMPTS_EXCEEDED`) instead. Malformed messages go to `cad:dead`.
- The database is the source of truth and the worker writes it directly via psycopg: `processing` is set with `UPDATE … WHERE id = $1 AND current_job_id = $2 AND status IN ('queued','processing')`; zero rows → the job was superseded, ack and drop. Results replace previous extraction rows (DELETE + INSERT/COPY) and set `processed` in **one** transaction guarded by the same `current_job_id`, and append the event (actor NULL). Handled failures set `failed` and are not retried automatically; only crashes are redelivered.
- A file stuck in `queued`/`processing` for more than 15 min can be reprocessed manually (new job id supersedes the old one).
**Consequences:** No BullMQ in 1a; Node-side job features (delays, repeat, UI) are not available for CAD jobs. Delivery is at-least-once and processing is idempotent per job id. BullMQ remains an option for Node-only jobs later.

## ADR-014: DWG conversion with LibreDWG (WASM) only — Accepted (2026-10-27)
**Context:** ADR-002 planned ODA File Converter with LibreDWG as a fallback. ODA needs a manual download and licence acceptance, and the build sandbox cannot reach apt mirrors.
**Decision:** The worker converts DWG to DXF with `@mlightcad/libredwg-web` 0.8.2 (LibreDWG compiled to WebAssembly), run by a small pinned Node script (`workers/cad/converter/dwg2dxf.mjs`), then reads the DXF with ezdxf. Verified on three real AutoCAD 2018 (AC1032) drawings up to 3.8 MB: same entity counts as reading the DWG directly and zero audit errors. Node is copied into the worker image from the pinned `node:22-slim` stage.
**Consequences:** No licence or system packages are needed. Node peaks near 0.9 GB RSS on the largest drawing, so the worker container needs about 1.5 GB. If a future drawing fails to convert, the file is marked `failed` (`CONVERTER_FAILED`) and the user can supply a DXF; ODA can be added behind the same `ConverterPort`.

## ADR-015: Redis client timeouts (lesson from the first end-to-end run) — Accepted (2026-10-27)
**Context:** redis-py 8 applies a 5 s socket timeout by default. The worker blocks in `BLMOVE` for 5 s, so an idle worker died with "Timeout reading from socket" and queued files stayed `queued`. The unit and integration tests used 1 s waits and did not see it.
**Decision:** The broker sets a 35 s socket timeout (longer than any blocking wait), a 5 s connect timeout and a health-check interval; the consumer loop converts Redis connection errors into `BrokerUnavailableError` and retries with exponential backoff (1 s up to 30 s) instead of crashing. Regression tests cover both.
**Consequences:** An idle worker survives indefinitely and recovers from a Redis restart. Lesson recorded: run the full API → Redis → worker → database path before closing a phase.

## ADR-016: Item work type, unit-price decimals and unit length — Accepted (2026-10-28)
**Context:** Testing the owner's real BOQ sheet (`boq_restored3_errors_yellow.xlsx`, 199 rows) against the 1a import rules showed three gaps: its "نوع الاعمال" column was ignored, 22 unit prices have 5 decimals (e.g. 5.59936), and 6 units are longer than 32 characters (e.g. "BULDING (more than 8 unit/flat per building)", 45 characters). The owner decided (2026-10-28):
1. Every item has a **work type** from a fixed list: `civil` (مدني), `installation` (تركيبات), `planning` (تخطيط). It is required on every item that has code, description, unit, quantity and price; it will be used for payment certificates, invoices, filtering and reports. The Arabic labels in the sheet are kept as they are, including items under section 2 labelled مدني.
2. **Unit prices** keep up to **6 decimals**; quantities stay at 4.
3. **Units** may be up to **64 characters**, and tables wrap long units instead of widening.
Section headings (rows without unit, quantity and price), empty quantities and the "مسلسل" header (not a code synonym) stay as they are.

**Decision:**
- Contracts (`packages/shared`): `WORK_TYPES` / `WorkTypeSchema`; `WorkOrderItemInputSchema.workType` required; `Decimal6StringSchema` for unit prices (`Decimal4StringSchema` stays for quantities); `ITEM_TEXT_LIMITS.unit = 64`. Import: `workType` is a required import field with header synonyms (نوع الأعمال, نوع العمل, work type, type of work, type de travaux); cell values must match `WORK_TYPE_SYNONYMS` after header normalisation, else the new row error `INVALID_WORK_TYPE`. `TOO_MANY_DECIMALS` carries `params.max` (4 or 6).
- Migration `0004`: `unit_price numeric(20,6)`; `amount` recreated as `numeric(38,10)` generated (4 + 6 decimals, still exact, never rounded); unit CHECK ≤ 64; `work_type text` with CHECK on the three codes and an index `(work_order_id, work_type)`.
- Items saved before 0004 have `work_type NULL` (no value is invented). The API returns `workType: null` for them and refuses an edit that does not set one (`VALIDATION_FAILED`, `reason: WORK_TYPE_REQUIRED`); the web form makes the user pick one.
- Web: work type select in the item form, a work type column in the item and import tables, and the unit column wraps (`max-w-48 wrap-break-word`). Mobile has no work-order screens yet; the same wrapping applies when they are built (Phase 3).
**Consequences:** Old Excel files without a work type column now fail with `REQUIRED_FIELD_UNMAPPED` (intended: the field is required). Line amounts may show up to 10 decimals until the rounding rule is decided for invoicing (Phase 5). Per-type totals and filters are built in Phases 2 and 5 on top of this column.

## ADR-017: CAD mapping and design revisions — Accepted (2026-10-28)
**Context:** Phase 1b turns a processed drawing (raw `cad_*` rows, SRID 0) into design features. The build plan asks for a mapping screen (layer/block → feature type, suggested from names), immutable published revisions, and stable feature ids across revisions.
**Decision:**
- Feature types: `route` (line), `box`, `hhi`, `joint`, `mh` (points) — `packages/shared/src/design/feature-types.ts`.
- Mapping (`cad_mappings`, one per CAD file, optimistic `version`): rules by `layer`, `block` (wins over its layer for inserts) or `text` (exact text on one layer, e.g. `NEW-HHI` on `RRR` → hhi). Targets are a feature type, `label` (texts are link candidates), `background` (tiles only) or `ignore`; layers without a rule are ignored. The PM also confirms `crsEpsg` (WGS 84 / UTM only) and picks the drawing unit (ADR-018). Name-based suggestions come from the plan's examples only and are never applied without the PM saving them.
- `POST /design-revisions` freezes the mapping (rules, EPSG, unit, factor) on a new `design_revisions` row and enqueues `cad.build_revision` on the existing Redis protocol (ADR-013; same reliability rules, guard = `design_revisions.current_job_id`). The worker builds features, text links (ADR-019), the diff (ADR-020) and a PMTiles archive, and leaves the revision `draft`. The PM reviews, then publishes: `rev_no` = next number in the project, and the revision is locked.
- Stable ids: `features` (identity, never updated) + `design_features` (one row per feature per revision, PK `(revision_id, feature_id)`). As-Built (Phase 4) will key on `features.id`.
- Immutability is enforced in the database: triggers reject any change to a published or discarded revision and to its features, text links and diff rows, and reject changes to a revision's frozen inputs at any time. At most one revision per project is `queued`/`building`/`draft` (partial unique index).
- Geometry: drawing coordinates × `metres_per_unit`, SRID = revision EPSG, 2D. `length_m` is a generated column (`ST_Length`, 3 decimals).
**Consequences:** Reprocessing a CAD file never changes a revision (revisions copy what they need, and the file cannot be deleted while a revision uses it). Fixing a published revision means building a new one. Drawings in local coordinates (not UTM) cannot become revisions until georeferencing is built (out of scope v1).

## ADR-018: Drawing units are a per-drawing setting — Accepted; Qalyub drawings are metres (owner, 2026-10-28)
**Context:** The Qalyub drawings declare `$INSUNITS=1` (inches), but their coordinates are clearly metres on UTM zone 36N (easting ≈ 325,000, northing ≈ 3,340,000; routes ≈ 3,700 m as planned). The owner has asked the technical office which is right; until then neither may be hard-coded.
**Owner decision (2026-10-28):** the drawings are in **metres**. `$INSUNITS=1` in the files is wrong and must not be used for lengths; the PM picks `m` on the mapping screen.
**Decision:**
- The drawing unit (`m`, `cm`, `mm`, `km`, `in`, `ft`) is chosen by the PM on the mapping screen, with **no default**. It is stored on the mapping and copied, with its exact factor (`metres_per_unit`, e.g. 0.0254), onto every design revision; the database checks factor = unit.
- The worker's CRS detection records the unit implied by the extents (UTM → metres) and the unit declared by `$INSUNITS`. When they differ it sets `unitsConflict` and adds the file warning `UNITS_CRS_MISMATCH`; the mapping screen shows both and the revision keeps `units_conflict`.
- Every metric value (feature geometry, `length_m`, link distances, matching tolerances) is computed after scaling by the revision factor, so later quantities go through this setting.
**Open:** whether `m` should become a per-project default (pre-selected on the mapping screen) instead of a choice with no default. Not implemented; the per-drawing choice and the `UNITS_CRS_MISMATCH` warning stay, so a future drawing in another unit is still caught. Revisions keep the unit they were built with.
**Closed by ADR-032 (owner, 2026-11-01):** drawing lengths are always metres; the per-drawing unit choice goes away when ADR-032 is implemented. Revisions already built keep their unit.

## ADR-019: Text linking and Arabic SHX conversion — Accepted (2026-10-28)
**Context:** Free texts near features carry their data (`F 36 C`, `1X2Way16/12`, `150.0M`, box ids `1-1`, B/P/U codes). Street names on layer `tx` use the legacy `xarb.shx` font and are stored as ASCII key codes.
**Decision:**
- Candidate texts = texts on layers mapped to a feature type or `label`, excluding texts consumed by `text` rules. Each is classified by the plan's patterns (whole text): `cable`, `duct`, `length` → routes; `box_id`, `box_bpu` → boxes; else `other` (listed, not linked). The meaning of B/P/U is not interpreted.
- Link = nearest feature of an allowed type within radius `15 × text height` (min 1 m), in metres. Confidence = `0.5 × (1 − d1/radius) + 0.5 × (1 − d1/d2)` (second term 1 without a second candidate). ≥ 0.8 → `auto`, else `review`; no candidate → `review` without a feature. These are tuning parameters, not business rules.
- A box's `code` is its best `box_id` link (auto or confirmed); the API recomputes it when the PM confirms, reassigns or rejects a box-id link.
- Unreadable texts (`readable=false`) become `unreadable` links in `review`: they can be linked or rejected, but their text is never guessed.
- SHX: the owner chose the conversion-table approach. `shx_arabic.json` `mappings` now holds the lowercase keys of the Arabic 101 layout (q→ض … /→ظ, b→لا). A text in a legacy font is decoded only when every character is a digit, space or a key in the table; any other character (upper-case keys, punctuation such as `U`, `H`, `F`) keeps the whole text `readable=false` for review. The backtick key (ذ on the layout) is not in the table yet because it was not observed in the drawings.
**Consequences:** Some street names become readable; the rest stay in the review list until the table is extended with confirmed upper-case forms. The 1a golden count of unreadable texts no longer applies and must be regenerated with the drawings.

## ADR-020: Revision matching and diff report — Accepted (2026-10-28)
**Context:** `features.id` must stay the same across design revisions; a new revision is matched to the old one by position, type and code, and conflicts go to the PM.
**Decision:** The worker matches each new feature to the base revision (last published) of the same type, one-to-one, in this order: (1) same source handle and within tolerance; (2) same non-empty code, unique on both sides; (3) nearest within tolerance (points: distance; routes: Hausdorff distance — or, for a route that was extended or shortened, the deviation of the shorter route from the longer one when it lies within tolerance of it and the shared part covers ≥ 80 % of the longer route), greedy by ascending distance. Tolerance 5 m. (The partial-overlap rule was added after the end-to-end run showed an 80 m route extended to 90 m losing its id.) When the second-best unmatched candidate is within tolerance and no farther than the best + 0.5 m, the match is a `conflict` (it still takes the nearest id and lists the others). Matched features are `unchanged` (≤ 1 mm and same code), `moved` (points), `reshaped` (routes), or `attributes_changed`; leftovers are `added` (new id) or `removed`. The diff is stored per revision (`revision_diff_items`) with counts on the revision. Publishing with conflicts or texts still in review needs an explicit acknowledgement.
**Consequences:** Ids survive small edits and re-saves; large moves (> 5 m) appear as removed + added and must be checked by the PM. Manual conflict resolution in the UI is a later task.

## ADR-021: Tile serving and its security — Accepted (2026-10-28)
**Context:** Design data must be visible on maps without exposing other projects. Martin can auto-publish every table it can read, which would leak all projects.
**Decision:**
- Martin runs with `auto_publish: false` and only the function source `tiles.design_features(z, x, y, query_params)` (`infra/martin/config.yaml`). It connects as `ftth_tiles`: no table privileges, `USAGE` on schema `tiles`, `EXECUTE` on that function only, read-only transactions. The function is `SECURITY DEFINER`, requires `p` (project) and `r` (revision) to match, serves only `draft` and `published` revisions, and returns an empty tile otherwise.
- Tile URLs are signed by the API: `POST …/design-revisions/:id/tile-url` (permission `design:read`) returns `{TILES_PUBLIC_URL}/design_features/{z}/{x}/{y}?p=…&r=…&exp=…&sig=…`, HMAC-SHA256 with `TILE_URL_SECRET`, valid 1 h. Caddy protects the tiles host with `forward_auth` to the API's `GET /tiles/verify`, which checks the signature and expiry from `X-Forwarded-Uri` in constant time (204, else 401).
- Offline/mobile: each built revision also gets a PMTiles archive (`network` and `background` layers, zoom 12–18, WGS 84 web mercator) in object storage, streamed by `GET …/design-revisions/:id/tiles.pmtiles` with HTTP Range support after the normal permission checks.
- Limits (security review): an archive is capped at 1,024 z12 seed tiles, 100,000 tiles and 256 MiB, else the build fails with `TILES_FAILED`; build statements time out after 120 s, and API requests waiting for a revision row being built give up after 5 s (409 `REVISION_BUSY`).

## ADR-024: Offline sync — outbox, `client_op_id`, conflict rules, resumable photos — Accepted (2026-10-30)
**Context:** Supervisors record work in the street with weak or no network (Phase 3). Every write must survive airplane mode, app restarts and retries, and never be counted twice (plan: "المزامنة", CLAUDE.md rule 4). Contracts: `packages/shared/src/execution/*`, detailed in `docs/phase-3-contracts.md`.
**Decision:**
- **Outbox on the device.** Saving an update writes one row to the local outbox (WatermelonDB) in the same local transaction as the update and its photo records. The outbox is drained in creation order, in batches of ≤ 50 operations, by `POST /projects/:projectId/sync/push`. Retries use exponential backoff with jitter (2 s → 5 min cap); network errors and 5xx/429 are retried, per-operation rejections are not.
- **Idempotency.** Every operation carries a client-generated UUID `clientOpId`. The server keeps `sync_operations (client_op_id PK, project, user, device, kind, payload sha256, result)` and inserts it in the same transaction as the update. A resend with the same id, user, device and payload hash answers `duplicate` with the first result; the same id with anything else is `rejected / OP_ID_REUSED` (never applied, never leaks the other row). Concurrent resends serialise on the primary key.
- **Records are immutable.** An execution update is an append-only fact (`execution_updates`, `execution_update_lines`), plus an `execution_update.recorded` event. Corrections are new updates (Phase 5 QC handles review); nothing is edited in place.
- **Conflict rules.** Updates on the same feature from several devices are **additive**: each is its own record and quantities add up (plan: "بجمع الكميات للتحديثات"). The server never rejects for business reasons it cannot judge; it attaches **flags** for QC instead: `ITEM_OVERRUN`, `GPS_FAR`, `GPS_MISSING`, `CLOCK_AHEAD`, `CLOCK_BEHIND`, `REVISION_OUTDATED`, `FEATURE_REMOVED`. Shape edits (last-writer-wins by server order) arrive with Phase 4. Hard rejections are limited to integrity and security: unknown feature/item/revision, feature outside the caller's zones, item of another work type, reused ids.
- **Clocks.** Ordering and cursors use only the server: `received_at` and a database sequence (`sync_seq`). The device clock (`capturedAt`) is kept as evidence and flagged when it is later than receipt + 5 min (`CLOCK_AHEAD`) or earlier than the publication of the revision the device used (`CLOCK_BEHIND`).
- **Pull.** `GET …/sync/changes?cursor=` returns updates in the caller's scope with `sync_seq > cursor` (status changes from Phase 5 QC bump the sequence). `GET …/sync/bootstrap` returns the offline bundle: latest published revision, its features in the caller's zones (project-CRS coordinates), the work-order items (no prices) with the recorded quantity, and settings. The PMTiles archive stays on its existing endpoint (ADR-021).
- **Zone scope.** Until Phase 2 adds feature-to-zone assignment, a feature is in a zone when its design geometry intersects the zone polygon (`ST_Intersects`). A zone without geometry contains nothing (fail closed). Project-wide roles see every feature.
- **Photos.** Metadata (id, requirement key, sha256, size) travels inside the update operation; bytes follow separately through a resumable upload: `GET …/sync/photos/:photoId` (received bytes) and `PUT …/content` with `Upload-Offset` and ≤ 1 MiB chunks. Only the user who recorded the update may upload; the server checks the offset, the declared size, the sha256 and the JPEG signature before writing the object (write-once key) and recording `execution_photo.stored`. On the device a photo is compressed (long side 1,600 px, JPEG 80 %, plan), watermarked (feature code, time, GPS) before hashing, and kept until the server confirms it is stored.
**Consequences:** A device can resend anything at any time. Updates whose photos are still uploading are visible to QC as such (`photos[].stored`). Partial uploads are kept in the database (`execution_photo_chunks`) until complete, bounded per user (`SYNC_UPLOAD_BACKLOG_MB`, default 64 MiB; finishing an upload is never refused) and discarded after `SYNC_STALE_UPLOAD_HOURS` (default 24 h) without a new chunk, by an hourly sweep — the device then restarts that photo. The sync routes are rate limited per user (`SYNC_RATE_LIMIT` 120/min for push, changes and bootstrap; `SYNC_UPLOAD_RATE_LIMIT` 600/min for photos; in-memory, single API instance like the auth limiter), and a push waits at most `SYNC_LOCK_TIMEOUT_MS` (5 s) for the project lock before answering 429; devices treat 429 as retry with backoff. All five are technical values the owner may tune. Open items for the owner are listed in `docs/PROGRESS.md` (Phase 3).

## ADR-025: Encryption of data kept on the phone — Accepted (2026-10-30)
**Context:** The supervisor app keeps photos, the offline drawing and work-order catalog, and the unsent updates (GPS, notes, quantities) on the phone, sometimes for days (Phase 3 security review, item 12). WatermelonDB's SQLite adapter has no database-file encryption (no SQLCipher), and patching its native code cannot be verified without a device.
**Decision:**
- Application-level encryption with XChaCha20-Poly1305 (`@noble/ciphers`, audited, pure JS): authenticated, and its 24-byte nonces are safe to draw at random for every message. Format: `0x01 | nonce | ciphertext+tag`; text columns store `v1:` + base64.
- One 32-byte key per installation, generated with the OS random source and kept only in the OS keystore (`expo-secure-store`, `WHEN_UNLOCKED_THIS_DEVICE_ONLY`: not in backups, not moved to another device, readable while the phone is unlocked).
- Sealed: photo files (`photos/<id>.sealed`; the sha256 sent to the server is of the plain JPEG, taken before sealing; the camera original and the resized copy are deleted), the cached offline bundle, the outbox `op_json` and the pulled updates' `json`. Readable: ids, project/user, feature id, states, attempt counts and the sync cursor — the outbox queries filter on them.
**Consequences:** A copied or rooted file system does not reveal photos, locations or notes without the keystore. Uninstalling the app (or a keystore reset) makes unsent local data unreadable; the outbox should be synced before. Plain data still exists briefly in memory and in the camera's temporary files until they are deleted. Encrypting a photo costs a few tens of milliseconds in JS; not measured on a device.

## ADR-028: Work-order lines come from the approved contract (Phase 2 step 2) — Accepted (2026-10-31)
**Context:** ADR-027 put the contract above projects (one project = one work order). Owner rules (2026-10-28 / 2026-10-31): same price as the contract; an item outside the contract is blocked; a quantity above the contract is fully blocked; the quantity is reserved when the work order is saved; one work order per project; a draft contract gives nothing ("approve it first"); each contract item at most once per work order; in an Excel import, any difference from the contract (price, description, unit, work type) is an error and the file must be fixed.

- A work-order line is `{contractItemId, quantity}`. Code, description, unit, unit price and work type are copied from the contract item and cannot be edited; editing a line changes only its quantity. Lines saved before this ADR (no contract item) are read-only (`LEGACY_ITEM`).

## ADR-030: As-Built edits — immutable edit records, separate approval, approved-state projection — Accepted (2026-11-01)
**Context:** Phase 4 lets supervisors change the drawing As-Built on the phone (move a symbol, edit a route, draw a route, insert a symbol, change a label) and lets the web approve each edit; quantities (Phase 5) must use the approved As-Built route length; the As-Built must export as DXF. Rules: design revisions are immutable; As-Built is separate state with the same feature ids; every change is an immutable event; every mobile write carries `client_op_id`; geometry in the project CRS (plan "قرارات معمارية", CLAUDE.md 3–5). Contracts: `packages/shared/src/asbuilt/asbuilt.schemas.ts`, `docs/phase-4-contracts.md`. Migration `0009_asbuilt.sql`.
**Decision:**
- **One edit = one immutable record** (`asbuilt_edits`, the plan's `geometry_edits`), sent as the sync operation `asbuilt_edit.record` through the Phase 3 push path: same `sync_operations` idempotency (duplicate / `OP_ID_REUSED`), same per-project lock, same pull cursor (`execution_sync_seq`). An edit carries the **full proposed geometry** (project-CRS metres), not a delta: the device collapses an editing session (`@ftth/geo` `EditSession`) into the final shape per feature on save. Kinds: `move` (point), `reshape` (route), `add_route`, `add_symbol`, `label`. No delete tool (not in the roadmap).
- **Separate approval.** An edit changes nothing until approved on the web (plan: "تعديلات الـAs-Built على الشكل ليها اعتماد منفصل"). Approve / reject are final; a rejection needs a reason; nobody reviews their own edit. Approval writes the projection `asbuilt_features` (approved state; a trigger accepts only geometry and labels coming from an approved edit) and an event; both review writes take the project lock and bump the edit's sync sequence so devices learn the decision.
- **Versions instead of silent last-writer-wins.** Each feature has an approved geometry version and label version (0 = design). An edit records the version it was drawn on (`baseVersion`). The server never rejects an edit for a stale base (ADR-024: business conflicts go to review); it flags `BASE_OUTDATED`, and approval of a stale edit is refused (409 `STALE_BASE`): the reviewer rejects it and the supervisor redraws on the current state. This is the most restrictive reading of the plan's "last-writer-wins للشكل": no approved shape is ever overwritten by an edit drawn on an older shape.
- **Added features** get a client-generated UUID that must not exist (`FEATURE_ID_REUSED`); an add is approved like any edit; later edits of an added feature need its add approved first. A rejected add keeps its id; a new attempt uses a new id.
- **Scope.** Recording needs `asbuilt:write` from an assignment; zone-scoped users may edit only features whose design geometry is in their zones (as in Phase 3) **and** whose proposed geometry lies entirely inside their zones (security review M1); adds must lie in their zones. Reviewing needs `asbuilt:review` (qc, pm, admin — assumption); exporting `asbuilt:export` (pm, admin — assumption).
- **Length.** Lengths are PostGIS `ST_Length` on project-CRS geometry rounded to 3 decimals (mm), stored as generated columns like `design_features.length_m`; the device's own length (`@ftth/geo polylineLength`) is display only. The read model "approved route length" = approved As-Built length if the feature has an approved geometry, else the design length of the latest published revision; added routes count once approved. Phase 5 reads it through `AsBuiltLengthsPort` only.
- **DXF export** runs in the CAD worker (job `cad.export_asbuilt`): design features of the latest published revision on their original layers, approved edited geometry on `ASBUILT_EDITS`, approved added features on `ASBUILT_ADDED`, with status texts; written once to storage and downloaded by pm/admin.
**Consequences:** Devices on Phase 3 builds keep working (new response fields default to empty). A newer design revision does not move As-Built geometry: approved edits stay keyed by feature id, and edits of a feature missing from the latest revision are flagged `FEATURE_REMOVED` and left out of the length read model. Open owner decisions are listed in `docs/PROGRESS.md` (Phase 4).

## ADR-032: Drawing placement — always UTM, always metres, foreign georeference ignored, symbol position from its geometry, correction by control points — Accepted (owner, 2026-10-30 / 2026-11-01); not implemented yet (issue #27)
**Context:** Two real drawings showed placement problems that the current pipeline (ADR-017, ADR-018) does not handle. «مساحى الدراويش» is UTM 36N but carries a CAD-Earth XRECORD (X offset −1540.42, Y offset +3031.79, code 70 = 32636) that made CAD-Earth show it ~3.4 km away; after resetting it, the drawing was still 11.4 m off and was fixed with one GPS point (cabinet 4-5 at 31.016593, 33.015613 → shift −8.61 E / +7.50 N). «مساحي بالم بلازا» (El Arish) is in Egypt 1907 / Red Belt (E ≈ 877,000, N ≈ 937,000), not UTM, although CAD-Earth tags it 32636; its `new-box` block has its geometry ~1,000 km from the block base point, so the insertion points of all 160 boxes are meaningless while the drawing looks right in AutoCAD. The worker reads symbol positions from `e.dxf.insert` (`workers/cad/cad_worker/adapters/ezdxf_reader.py`).
**Decision:**
- **Project CRS is always WGS 84 / UTM** (sites so far: zone 36N, EPSG 32636). A drawing in another CRS (e.g. Egypt 1907 belts) is converted to the project's UTM zone with a datum transformation; it is not rejected. Supersedes the "local coordinates cannot become revisions" consequence of ADR-017 for drawings whose source CRS is known.
- **Drawing lengths are always metres**, whatever `$INSUNITS` declares. This closes the open point of ADR-018: the unit is no longer a PM choice; `$INSUNITS` is kept as information only and a mismatch stays a warning.
- **Georeference stored by other tools is ignored** (CAD-Earth XRECORDs, AutoCAD GEODATA and similar). Only the drawing's own coordinates are used. Reason: such data is hidden from the user, can be stale, wrong (wrong EPSG tag) or applied twice.
- **A symbol's position is the centre of its drawn geometry** (the rendered block's extents), never the INSERT insertion point. This applies to boxes, cabinets and every other block-based feature.
- **Location correction by control points.** The user picks a point on the drawing and enters its Lat/Lon (converted to the project UTM):
  - 1 point → translation only.
  - 2 points (preferred) → translation + rotation; scale too when the user reports a scale problem (two points fix a similarity transform).
  - 3 or more points → translation + rotation + scale, least-squares fit, with the residual of each point in metres.
  - A scale factor further than 0.1 % from 1 shows a warning before it is applied.
- **The original file is never changed.** The correction (control points, transform, author, time) is stored with the mapping and frozen on the design revision like the unit and EPSG (ADR-017); a new correction means a new revision. Corrected copies of a drawing are exported as DXF only.
**Open:**
- Datum parameters Egypt 1907 → WGS 84: the published regional values (ΔX −130, ΔY +110, ΔZ −13 m, accuracy of a few metres) unless the survey office provides local parameters. The control-point correction removes the remaining offset either way.
- Who may correct a drawing's location: PM only, or also supervisors sending GPS points from site for PM approval.
**Consequences:** The mapping screen loses the unit picker and gains a placement panel (source CRS, conversion, control points, residuals). The worker needs the source-CRS detection for Egyptian belts, the datum conversion, geometry-based symbol positions and the removal of foreign georeference. Acceptance and test cases: the two drawings above (cabinet 4-5 within 0.5 m after a one-point correction; all 167 Palm Plaza boxes at their drawn positions).

## ADR-033: Cabinets, rings, shape-based point items, microduct kinds, drawing warnings — Accepted (owner, 2026-11-03); not implemented yet (issue #32)
**Context:** The owner chose the Darawish drawing (`مساحى الدراويش.dwg`) for the golden run instead of Qalyub, whose drawing has known problems. ## ADR-035: Placing a drawing in the program — Red Belt conversion, control points from Lat/Lon or KML/KMZ, map preview with Move / Rotate / Scale, PM and supervisor roles — Accepted (owner, 2026-11-04 / 2026-11-05); completes ADR-032; not implemented yet (issue #27)

## ADR-036: Subcontractors — shared list, registration on a work order, capped quantities, dated prices — Accepted (owner, 2026-11-07); part 1 of 3
**Context:** Phase 2 lists "client and subcontractor prices". The client price is the contract price (ADR-027, ADR-028). Before this ADR a subcontractor existed only as a user role (`contractor`, no permissions) assigned to a zone; there was no company record to carry prices. The owner answered nine questions on 2026-11-07, one at a time.
**Decision (owner):**
- Only platform admins register a contractor and later edit its quantities and prices; PMs read (`contractors:read`).
- Contractors are a **shared list**, entered once: name, contact person and phone (required), commercial register and tax card (optional). On each work order (أمر التكليف / المشروع) the admin picks a contractor from the list and records the **registration date** and the **lines** (required).
- A contractor line is a **work-order line** (so the contract's description and unit) plus a **scope of work** (نطاق الشغل, free text; empty = the whole line). One contract line can be split between contractors by scope (owner's example: box item 2-12-4-8 → fix bracket / install box / splice box). The owner has no predefined breakdown per item, so the scope is written in the contractor's sheet.
- **Quantity:** per work-order line and scope, Σ over every contractor ≤ work-order quantity. A line given whole and scoped lines never mix on one work-order line.
- **Price:** the scopes' prices on one work-order line add up to **at most the contract price** (owner). A scope counts at the highest price ever recorded on it (any contractor, any date); a whole line counts as one scope.
- Contract BOQ, work-order lists and **contractor lists are uploaded as sheets**, never typed line by line (owner). Contractor sheet columns: code, description, unit, scope, quantity, price; a split line appears on several rows with the same code. Rows are checked like the work order against the contract (any difference in description or unit is an error) plus the scope rules, before saving.
- **A price can change from a date**; work before that date keeps the old price. Prices are a dated history, never overwritten.
- (Part 2) In each execution update the **supervisor picks the contractor** who did the work, among the contractors on that line. A quantity above that contractor's quantity is **rejected** (not flagged), and the contractor's quantity must be raised first.
- (Part 3) The contractor gets a **read-only login**: its own lines, quantities, prices, recorded work with QC status and reason, and its invoices (Phase 5). Never client prices or other contractors; enforced on the server.
- Active / suspended status was offered; the owner left it out.
**Confirmed by the owner (2026-11-07):** scopes are compared after normalising spaces, case and Arabic letter forms (`scopeKeyOf`); heading rows and rows with an empty quantity in a contractor sheet are skipped as in the work-order import; an uploaded sheet is kept when its registration is removed. **Assumptions (most restrictive reading, to confirm):** contractor names are unique ignoring case and outer spaces; a line quantity is above 0; the registration date never changes (remove and register again); the first price starts on the registration date and each new price strictly after the latest one (no back-dating); a registration or line can be removed while no work is recorded on it (part 2 adds that check); a work-order line given to a contractor cannot be removed, nor reduced below the contractors' sum, and a work order with contractors cannot be deleted.
**Consequences:** shared contracts `packages/shared/src/contractors/contractor.schemas.ts` and the import field `scope`; migration `0013_subcontractors.sql` (0012 is PR #42's placement) with triggers that lock the work-order row for the per-scope quantity cap and the scope price sum, check dates, keep prices append-only and require a price on every line, plus `contractor_import_files`; API module `contractors` (contractor list, sheet preview / commit, quantity edit, dated price, removals, PM read route); admin screens (contractor list, contractors section, upload page) and a PM read-only page. Part 2 changes the execution sync contract (Phase 3) and the mobile update flow; part 3 the permissions of the `contractor` role and a link from user to contractor. Next ADR: 037, next migration: 0014.

## ADR-040: Two drawings per work order — General (رئيسي) and Secondary (ثانوي); their reading rules, checks and quantities — Accepted (owner, 2026-11-11); extends ADR-032/035/038/039
**Context:** Until now a project had one CAD file per design revision and one draft at a time. The owner explained (2026-11-11) that every work order has two drawings, the General (main network: handholes, joints, the feeder cable to every cabinet) and the Secondary (from each cabinet to the building boxes), and walked through both drawings of Al-Fath (Rabaa) screenshot by screenshot. Layer, block and text-layer names below are the Al-Fath examples: they change from drawing to drawing; the PM maps them per file (ADR-014/033), the rules are about meaning.
**Decision (owner):**
- **Structure.** Contract → several work orders; work order = project. Each work order has exactly **one General and one Secondary** (one file per kind). Uploading a General when one exists asks «is this a new version of this work order's General?»: yes = new version, no = refused; same for the Secondary. Both go through the normal processing (upload, mapping, placement, build, errors, corrections, publish conditions of ADR-032/035/038). One can be uploaded and corrected before the other exists, but **publishing is only for both together**, with zero errors in both. The Secondary's placement is set automatically from the cabinets shared with the placed General (same name → control point), with the per-point error of ADR-035; the PM can add or remove points. After publishing, the supervisor is asked «رئيسي ولا ثانوي» and works on the chosen drawing.
- **Shared cabinets.** A cabinet appears in both drawings and is matched **by its name** (label, e.g. 1-7). A name in one drawing but not in the other, or a different cabinet count, is an error. Work recorded on a shared cabinet in one drawing cannot be recorded again in the other.
- **Upload questions per kind.** General: «is the whole route pulled through existing pipes, or is there a part with new pipes that needs trenching?». No = the whole route is *pull*; yes = the trench parts are marked on «عارض الرسومات» with their length, the rest stays *pull* (one route can mix both). Secondary: no question; everything is *trench*; a different case shows up when the supervisor records the work.
- **General reading:** duct routes (any layer the PM maps); handholes = symbol + number (e.g. 04A) + type from the list DH (70×70×70 cm inside), HH-I, HH-II (CH), MH-I…MH-IV; joints inside handholes (e.g. joint up to 144 fibres); the main cable (e.g. 144 or 36 core) is branched at each joint into one cable per cabinet (e.g. 12 core) and continues with the remaining fibres; every segment between two points carries a **bundle label** (length, type, duct size, e.g. «500M/4way 16/12») and a **cable label** (length, cores, e.g. «520M/144Core F.O»); «SP n» on the main cable = spare cores.
- **Secondary reading:** box = box symbol; its **name is its number** under the cabinet written next to it (e.g. cabinet 1-3, box 9); a box belongs to the cabinet written on it even if it sits in the neighbouring zone. Box **type comes from the symbol's drawn shape** (not its block name, not global): the program groups boxes by shape with a picture and a count, the PM picks the type for each shape (e.g. «بوكس 8 فرعة بسبليتر 4»), and a type text is shown next to each box in the viewer and in the downloaded DXF. Fibre cable per box (e.g. F4C = 4 core) with its length from the cabinet. Bundles 1way / 7way / 12way / 24way with a label = type + duct size + length; the **written length counts**. One **connector per 1way** leaving another bundle (two drops from one point = two connectors, whatever the symbols drawn). Bundle end «SPn(7/3.5)» = n spare singles; every spare gets **two end caps** of its size (bundle end + cabinet side). Cabinet circles: name, type (e.g. 22U = body 22), number of boxes (e.g. 22B); «nP» is information only. Every cabinet has a **zone** (any line around the cabinet and its boxes; open lines allowed; colour free; display only). One box protector («خوصة») per box, not drawn.
- **Cabinet contents (secondary quantities), example 1-7:** body (22U), concrete base, Main ODF, one fusion splice + pigtail + coupler per core of the incoming cable terminated on the ODF (12), LGX splitters (ratio = total split 1:32 or 1:64 ÷ box splitter ratio, e.g. 1:8; count = ceil(boxes ÷ outputs), e.g. 3) on a 4U rack chassis (up to 12 LGX), patch cords Main ODF → each LGX, Secondary ODF (≥ outputs), patch cords for the **used** LGX outputs (22), one 4-core building cable and one box (splitter 1:4) per box, 88 subscriber outputs.
- **Trench / pull quantities:** trench length = bundle length − 4 m (connector → box) or − 3 m (cabinet → connector); a shared path is dug once; volume = length × width × depth of the excavation item (m³). *Pull* segments have no trench quantity.
- **Checks — errors (block publishing):** any text whose content contradicts its layer's type (e.g. «Joint 144» on a joint-36 layer, a bundle label type ≠ the line's layer); handhole without a type or with a type outside the list; handhole written but not drawn; two boxes with the same number under one cabinet; a box without a 1way reaching it; cabinet box count written ≠ boxes drawn under it; cabinet without a zone; spare cores written ≠ main cores − branch cores; cable shorter than its bundle or spare under 15 m; shared-cabinet name or count mismatch between the two drawings. **Warning only:** cable longer than its bundle by more than 30 m. **No check:** written bundle length vs drawn length (written counts); zone shape.
**Consequences:** delivered in parts, each with its own PR: (A) structure — drawing kind per CAD file, versions, one draft per kind, publish both together, supervisor choice; (B/C) reading the General and the Secondary; (D) the General upload question and trench marking on the viewer; (E) box type by shape; (F) the checks; (G) automatic Secondary placement; (H) quantities against the work-order items (with Phase 2 points 2-ب and 2-د). Next ADR: 041, next migration: 0018.

## ADR-041: Reading the General and the Secondary by meaning — text roles, zone layers, feature readings, the ADR-040 checks — Proposed (architect, 2026-11-11); technical design of ADR-040 parts B, C and F; open questions below go to the owner
**Context:** ADR-040 gave the owner's meaning of both drawings. The mapping (`cad-mapping.schemas.ts`) only says which layers are which feature type or `label`; a label layer has no meaning, so a box code is "any N-N text near the box" (ADR-019) — wrong for the Secondary, where that text is the cabinet name. Layer and block names change between drawings; the PM maps them per file. The design therefore puts the meaning on the **mapping rules**, read by the worker per drawing kind; the business rules are ADR-040's, only the mechanics are decided here.
**Decision (technical):**
- **Mapping additions** (`layer` rules only; `cad-mapping.schemas.ts`, `text-roles.ts`):
  - `textRoles: TextRole[]` (≥ 1, unique) — what the layer's texts mean. Roles: `box_number`, `box_cabinet`, `box_cable_type`, `box_cable_length`, `bundle_label`, `bundle_spare`, `cable_label`, `cable_spare`, `handhole_number`, `handhole_type`, `cabinet_info`. Allowed when the target is `label` or the role's own feature type (`TEXT_ROLE_FEATURE`, e.g. `cabinet_info` on the cabinet layer CABINA). One layer may carry several roles (Al-Fath EXCH = bundle_label + cable_label + cable_spare). `cabinet.role` (main/sub) is unchanged; the new key is separate on purpose.
  - `ways: 1…288` on `route` rules — the bundle type (1way, 7way, 12way, 24way; General «4 way»). Suggested from the layer name (`suggestBundleWays`). `kind` stays free text for totals.
  - target `zone` (Secondary): curves around a cabinet and its boxes; never a feature, not a move-layer target.
  - Roles allowed per kind (`TEXT_ROLES_BY_KIND`); `zone` only in a Secondary. The API refuses others on PUT …/mapping (422, `ROLE_NOT_FOR_KIND` / `ZONE_NOT_FOR_KIND`, `mappingKindProblems`). Role suggestions come from the layer's sample texts (`suggestTextRoles`, ≥ 30 % of samples read).
  - **Reading mode** (`readingModeOf`): `legacy` when no rule has `textRoles` and none targets `zone` — the build is exactly Phase 1; `roles` otherwise. Old mappings and revisions keep working unchanged; the web must keep `textRoles` / `ways` when it re-saves a rule.
- **Reading a text** (`readRoleText`): whole trimmed text, the first role in `TEXT_ROLES` order (among the layer's roles) whose pattern matches; no match = the text means nothing (never guessed). Formats are the owner's examples: «9», «1-3», «F4C», «398M», «1way 7/3.5» + «10.0M» (Secondary length is its own text), «500M/4way 16/12», «520M/144Core F.O(…)», «SP 48», «SP3(7/3.5)», «04A» / «CH01», «HH1» / «DH» / «CH» / «MH-IV», «1-7» «22U» «22B» «2P». Written lengths become metres with 3 decimals as strings (`writtenMetres3`, no floats). TS (`text-roles.ts`) and Python (`text_roles.py`) carry the same patterns and the same test table.
- **Linking role texts to features** (worker, after corrections are applied): candidates are features of `TEXT_ROLE_FEATURE[role]`; radius = ADR-019 `link_radius_m(text height)`; distance to the point, or to the line for routes (STRtree as `text_links.py`). Per role, pairs are made **one-to-one, nearest first** (the `pair_labels` algorithm, ties by handles): a feature takes at most one text per role — except `bundle_label`, where a route takes one type text and one length-only text, and `bundle_spare`, which a route takes up to two (one per end). A text goes to at most one feature. Texts on role layers are **not** written to `text_links` (no review items) and are left out of the Phase-1 `labels_for` pairing and `_labels_without_length`; every other Phase-1 check runs as before in both modes.
- **What is stored** (`feature-reading.schemas.ts`): `design_features.attrs.reading` = `{of: 'box', cabinet, number, cableCores, cableLengthM}` | `{of: 'route', ways, labelWays, ductSize, writtenLengthM, cableCores, cableLengthM, spareCores, spares[], connectors}` | `{of: 'hhi', number, type, typeText}` | `{of: 'cabinet', name, type, boxCount, ports, boxesDrawn, zoneHandle}`, each with `texts` (handles per role). Feature `code` in roles mode: box = `boxCode(cabinet, number)` ("1-3/9"; a box belongs to the cabinet written on it wherever it sits), hhi = number, cabinet = name. `design_revisions.counts.reading` (`ReadingTotalsSchema`) = bundles per ways/duct size with Σ **written** length, connectors, spares and end caps per size, cables per cores, handholes per type — kept for part H. No new columns.
- **Counting (Secondary):** a **connector** = a 1way route (rule `ways` = 1) end lying within `CONNECTOR_TOUCH_M` of a route of another `ways` (anywhere on it, not only its ends); each end counts once, two drops from one point = two, drawn connector symbols are not used. A **spare** «SPn(size)» = n singles of that size; **end caps** = `END_CAPS_PER_SPARE` (2) × n. A **zone**: zone curves touching within 0.05 m form one group; its area is the convex hull of its vertices (open lines allowed); a cabinet has a zone when it lies in a group's hull (smallest hull wins → `zoneHandle`). `boxesDrawn` = boxes whose `box_cabinet` has the cabinet's `cabinetNameKey`. `CONNECTOR_TOUCH_M` and `BOX_REACH_M` are technical tolerances, set and recorded by the worker on the Al-Fath golden run.
- **Checks** (worker, roles mode; codes in `drawing-problems.ts`; `params` per place in `DrawingProblemParamsSchema`). Place `handle` = the text to fix for text-fixed problems, else the symbol; `params.featureHandle` names the other one.
  Each line: code — drawing kind — when — place → fix tool (ADR-038). All block publishing except the last.
  - `LABEL_TYPE_MISMATCH` (Phase-1 code, extended) — both — a route's `labelWays` ≠ its rule `ways` (`params` role, expected, found); points as in Phase 1 («Joint 144» on a joint-36 layer) — label text → `set_text`, or `move_layer` of the route.
  - `LABEL_MISSING` (extended) — both — a required role text is missing: box `box_number` / `box_cabinet`; hhi `handhole_number`; **sub** cabinet `cabinet_info` name (`params.role`, `field`); `suggestedLayer` = a layer carrying the role — symbol → `add_text` on `suggestedLayer`.
  - `LABEL_LENGTH_MISSING` (extended) — both — a route with a bundle type but no written length, or a cable label without length — type text → `set_text` (the combined «455M/12way 7/3.5» form is accepted).
  - `HANDHOLE_TYPE_MISSING` — general — hhi without a type text — symbol → `add_text`.
  - `HANDHOLE_TYPE_UNKNOWN` — general — type text outside DH, HH-I (HH1), HH-II (CH), MH-I…MH-IV — text → `set_text`.
  - `HANDHOLE_NOT_DRAWN` — general — `handhole_number` text with no hhi within its radius — text → `add_item` on a hhi layer.
  - `BOX_NUMBER_DUPLICATE` — secondary — same `number` under the same `cabinetNameKey`; one place per box — number text → `set_text`.
  - `BOX_NOT_REACHED` — secondary — no 1way end within `BOX_REACH_M` of the box — symbol → AutoCAD.
  - `CABINET_BOX_COUNT_MISMATCH` — secondary — written «nB» ≠ `boxesDrawn` — «nB» text → `set_text`.
  - `CABINET_ZONE_MISSING` — secondary — cabinet inside no zone group (also when no `zone` layer is mapped) — symbol → AutoCAD, or map the zone layer.
  - `SPARE_CORES_MISMATCH` — general — «SP n» ≠ main cores − Σ branch cores (`expected`, `found`, `mainCores`) — SP text → `set_text`.
  - `CABLE_SLACK_TOO_SHORT` — general — per route with both lengths, cable − bundle < `CABLE_SLACK_MIN_M` (15; a shorter cable included) — cable label → `set_text`.
  - `CABLE_SLACK_TOO_LONG` — general — cable − bundle > `CABLE_SLACK_WARN_ABOVE_M` (30) — cable label → `set_text`. **Warning: does not block.**
  Compared as decimals; 15 and 30 themselves pass. *Spare cores (provisional, see Q4):* main cores = cores of the cable label on the route the «SP n» text links to; branch cores = Σ cores of the cable labels (one per route) with fewer cores than the main.
- **Blocking is decided by the code** (`DRAWING_PROBLEM_BLOCKS`, `blocksPublishing`), never by the stored severity (Phase-1 codes are stored `warning` and still block, ADR-038). `DrawingProblemList.total` and the readiness counts are **blocking places only**; `warningTotal` / `PublishReadiness.warningCount` show the rest.
- **Cross-drawing check (API, needs both drafts):** at readiness and publish the API reads the **sub** cabinets' `code` of both open drafts and runs `compareCabinets`: ok when both counts are equal, no cabinet is unnamed and every name (`cabinetNameKey`) is in both. New check key `cabinets_match` (not ok without the other draft; count = unnamed + names missing, both sides) and `PublishReadiness.cabinets`; publish refuses with `CABINETS_MISMATCH` + the comparison, checked after both drawings' own blockers and before `OPEN_ITEMS`. A legacy-mode drawing has no cabinet names, so it cannot pass: the PM maps a `cabinet_info` layer (or names the cabinets with `add_text`).
- **Database:** migration `0020_drawing_problem_codes.sql` widens the `cad_file_corrections.problem_code` check to the new codes. Everything else uses existing jsonb columns.

## ADR-042: The General's installation question and trench marks; automatic Secondary placement from the General's cabinets — Proposed (architect, 2026-11-12); technical design of ADR-040 parts D and G; open questions below go to the owner
**Context:** ADR-040 (owner, G14–G17): bundles are installed by **trench** (dig, lay, backfill, blow the cable) or **pull** (pull through existing pipes, then blow the cable). The General is pull; after uploading it the PM is asked «المسار كله سحب في مواسير قديمة، ولا فيه جزء محتاج حفر وتركيب مواسير؟»; no new pipes = all pull; yes = the trench parts are marked on «عارض الرسومات» (ADR-039) with their written length, the rest stays pull, one route can mix both. The Secondary is not asked: all trench (exceptions come from the supervisor's records later). ADR-040 Q9: the Secondary's placement is set automatically from the cabinets shared with the placed General, with the per-point error of ADR-035, and the PM can add or remove points. Owner principle: anything unclear is an error.
**Decision (technical, part D — `cad/installation.schemas.ts`):**
- **The answer and the marks belong to the General CAD file**, not to the mapping: they are site facts about that file's route and reference its drawing handles; the mapping stays the reading rules. Both are append-only with who / when, like ADR-038 corrections, and are **frozen on the design revision at creation** (`design_revisions.installation` = `FrozenInstallation` {answer, answerId, marks [{id, routeHandle, lengthM}]}); a later answer or mark needs a rebuild («طبّق وابنِ من جديد»; `installationChangedSince` tells the web). Null on a Secondary and on revisions built before 0022 (a General then reads as unanswered).
- **Answer** `pull_only` | `has_trench`: each change is a new row (`cad_file_installation_answers`, never updated or deleted, latest in force, ≤ 100 per file). `pull_only` is refused while marks are in force (`TRENCH_MARKS_ACTIVE`: withdraw them first).
- **Trench mark** = a route piece picked on the canvas (its top-level drawing handle) + the trench length **written** by the PM (metres, decimal string, > 0, ≤ 100,000, ≤ 3 decimals; `TrenchLengthSchema`). Several marks may sit on one route; no position along the route is stored (length only, see Q3). Added only while the answer is `has_trench` (`ANSWER_NOT_TRENCH`), only on a processed, current General (`NOT_GENERAL_DRAWING`, `FILE_SUPERSEDED`, `NOT_PROCESSED`), with a handle that is a curve of the file's extraction (`ROUTE_NOT_FOUND`); withdrawable once, never deleted (`cad_file_trench_marks`, ≤ 2,000 in force, ≤ 8,000 rows per file). Permission `design:write` (as corrections); reads `cad_files:read`.
- **Check** (`evaluateInstallation`, pure, used by readiness, publish and part H) on the revision's frozen installation and its route features; a marked handle resolves through the frozen `merge_routes` corrections to the smallest piece handle (`routeKeyResolver`, as the worker's `merge_curves`). Issues, all blocking: `QUESTION_UNANSWERED`, `TRENCH_NOT_MARKED` (`has_trench` with zero marks), `MARKS_WITH_PULL_ONLY` (defence; the API prevents it), `MARK_ROUTE_MISSING` (handle is no route of the revision), `ROUTE_LENGTH_UNKNOWN` (marked route without a written bundle length), `TRENCH_LONGER_THAN_ROUTE` (Σ marks on a route > its written length; equal passes). Compared as decimals (millimetres in bigint), never floats.
- **Publish:** new check key `installation` (General: issues count; Secondary: always ok, count null; `other_drawing` also needs the other General's installation clear) and blocker `INSTALLATION_UNCLEAR` {issueCount, issues} after the drawing's own `PROBLEMS_OPEN`, before `CABINETS_MISMATCH`; `PublishReadiness.installation` carries the report.
- **Totals for part H are derived, not stored:** `InstallationTotals` {trenchM = Σ marks, pullM = Σ written lengths of every route − trenchM, routesWithoutLength, marked routes with trench / pull}, only when the check is ok; computed from the published revision, whose inputs are immutable. The Secondary's trench comes from its own reading totals (ADR-041) in part H.
- **Events:** `installation_answer.answered` {cadFileId, answer, previousAnswer}, `trench_mark.added` / `trench_mark.withdrawn` {cadFileId, routeHandle, lengthM}.
- **API:** `GET …/cad-files/:f/installation` (`InstallationState`), `PUT …/installation/answer` (`SetInstallationAnswerRequest` → `InstallationAnswerRecord`), `POST …/installation/trench-marks` (`CreateTrenchMarkRequest` → 201 `TrenchMark`), `POST …/installation/trench-marks/:markId/withdraw` (→ `TrenchMark`), `GET …/design-revisions/:r/installation` (`InstallationReport`); refusals in `INSTALLATION_WRITE_REFUSALS`. Revision create / rebuild freeze the installation in the same transaction as the corrections.
- **Web:** a question card on the General's file / mapping page and on the draft page while unanswered (two buttons, the owner's wording); with `has_trench` the canvas gets a «حفر جديد» tool: select a route piece → type the length → saved; marks are drawn on their route with their length and listed under the canvas with withdraw; a «rebuild needed» notice when the live state differs from the draft; the checklist row `installation` lists the issues with «اعرض الموضع على الرسمة».
**Decision (technical, part G — `cad/secondary-placement.schemas.ts`):**
- **New control-point source `general_cabinet`** (Secondary files only: the API refuses it in a General's mapping, `POINT_SOURCE_NOT_FOR_KIND`, `placementKindProblems`). `MAX_CONTROL_POINTS` 50 → 200 (one point per shared cabinet; Rabaa has 81).
- **Where the positions come from:** General = the latest `draft` or `published` revision of the **current** General file, which must carry a placement with a control point in use; its **sub** cabinets' `code` (name) and `anchor` (project CRS) are converted to Lat/Lon by the API through `@ftth/geo` (`createProjectCrs().toWgs84`; ControlPoint stores Lat/Lon). Secondary = the latest `draft` or `published` revision of the current Secondary file: its sub cabinets' `code` (read by roles, so a name added by a correction counts) and their **drawn centre in drawing units**, stored by the worker from now on as `attrs.drawingAt` on every point feature (after corrections, before placement — the point the placement screen lists). The extraction-based placement items (ADR-037) are not used: their `names` are nearby-text hints, not the read name (no guess).
- **Matching** (`matchSharedCabinets`, pure): same `cabinetNameKey`, sub cabinets only (owner answer 1 of ADR-041); a name drawn twice on either side, an unnamed cabinet, a name in one drawing only, or a Secondary cabinet without `drawingAt` gives no point and is listed (`unmatched`). Points are sorted by name, ids `gc-<name>` so a new suggestion replaces the old (`withGeneralCabinetPoints` keeps the PM's typed / KML / GPS points first and a cabinet the PM left out stays left out), capped at 200 (`truncated`).
- **Errors per point** as ADR-035: the web fits with `solvePlacement` and flags far points; the PM leaves them out (`excluded`) or adds / removes points; Al-Fath's 6–8 m (1-2 ≈ 22 m) differences between the drawings will show and are expected.
- **API:** `GET …/cad-files/:f/placement/general-cabinets` → `SecondaryPlacementSuggestion` (read-only, no event), or 409 `SecondaryPlacementRefusedDetails`: `NOT_SECONDARY`, `NOT_CURRENT`, `SECONDARY_BUILDING`, `SECONDARY_NOT_BUILT`, `SECONDARY_REBUILD_NEEDED` (no `drawingAt`), `GENERAL_BUILDING`, `GENERAL_NOT_BUILT`, `GENERAL_NOT_PLACED` — each a clear message, nothing guessed.
- **Web:** on the Secondary's placement panel, «من كبائن الرئيسي»: fetched automatically when the placement has no point yet (else on the button), filled into the panel unsaved, map preview with errors per point, lists of unmatched names; the PM saves the mapping and rebuilds as today. `general_cabinet` points are read-only except exclude / remove.
**Database:** migration `0022_installation_trench_marks.sql`: `cad_file_installation_answers` (append-only), `cad_file_trench_marks` (withdraw once), both General-only by trigger; `design_revisions.installation` (General only) added to the frozen-inputs guard. Part G needs no table (`attrs.drawingAt` is jsonb).
**Open questions (owner; the cautious reading is used meanwhile):**
1. A new version of the General: are the answer and the marks carried over? (Now: no — handles can change; the question is asked again and the previous version's marks are shown as information.)
2. Is the trench length compared with the route's written bundle length (Σ marks ≤ written), or may it exceed it? (Now: may not; `TRENCH_LONGER_THAN_ROUTE` is an error.)
3. Must the PM show where along the route the trench part lies (two points on the line), or is route + length enough? (Now: route + length.)

## ADR-043: Box type by the drawn shape — shape signatures, a gallery per revision, a work-order line per shape — Proposed (architect, 2026-11-12); technical design of ADR-040 part E
**Context:** ADR-040 (owner, C21/C22, 2026-11-12): there are many box types and each should have its own symbol, but drawings use symbols freely — the same symbol means «بوكس 8 فرعة بسبليتر 4» in one drawing and «بوكس 4 فرعة بسبليتر 4» in another, so the meaning is **per drawing**. Boxes carry no type text or attribute (Al-Fath Secondary: 197 boxes, one block `box c`, no attributes). The program groups the boxes by the **drawn shape** of their symbol (how it looks, not the block name), shows a picture and a count per shape, and the PM picks the type in front of each shape. Owner decision 2026-11-12 (option أ): the type list is the **lines of the project's work order** (BOQ); the PM picks a work-order line per shape, so part H counts the boxes on that line. The type then shows as a text next to every box in «عارض الرسومات» and in the DXF downloaded from the program. Owner principle: anything unclear is an error. Contracts: `packages/shared/src/cad/box-types.schemas.ts`.
**Decision (technical):**
- **Shape signature (worker, `domain/box_shapes.py`, pure):** per box, from what is drawn — `block`: the INSERT's geometry exploded (nested blocks included, ATTRIBs left out, constant TEXT / MTEXT kept as text + position + height), taken relative to the insertion point with the **insert rotation undone** (mirroring, non-uniform scale and OCS flips are kept: they look different); `shapes` (ADR-033 closed-shape groups): their geometry as drawn (no rotation is known, none is removed); `text` (`text` rule): the trimmed upper-cased text; `none` (`add_item` correction): nothing drawn, signature `none`. Then: curves flattened (circles / arcs at a fixed 64 segments per full turn, splines and bulges as `flatten.py`), hatches as their boundary loops + a solid/pattern flag; everything broken into segments; moved so the bbox centre is 0,0; divided by the larger bbox side (uniform size removed); coordinates quantized to 1/1000; zero-length and duplicate segments dropped, each segment's ends ordered, the list sorted; SHA-256 of the canonical text with the source and `BOX_SHAPE_ALGORITHM_VERSION` → `v1-<hex>`. Colour and layer are not part of the shape. **When in doubt it splits, never merges**: two drawings of one look that differ (e.g. a symbol drawn as a polyline vs separate lines with a split segment, or a closed-shape group rotated) give two shapes; the PM picks the same line for both. Two block names drawn alike give one shape.
- **Where it is computed and stored:** INSERT signatures at **import** (the extraction already explodes each insert for its drawn centre, ADR-032): `cad_inserts.shape_signature` and, per distinct signature of the file, its preview in `cad_file_shapes` (≤ `MAX_FILE_SHAPES` 2,000 previews; beyond, signatures still stored, preview null). Closed-shape groups, text-rule and added boxes at **build** from the extracted rows. The build writes the **gallery** of a roles-mode Secondary to `design_revisions.box_shapes` (`BoxShapeGallery`: every distinct shape of the revision's boxes with its source, count, ≤ 20 block names, ≤ 5 sample handles, preview; sorted by count; ≤ `MAX_BOX_SHAPES` 200 listed, `shapeCount` exact; `boxesWithoutShape` for inserts of files processed before 0023) and `attrs.reading.shape` on each box. Previews are normalized paths (≤ 256 vertices, ≤ 128 paths, ≤ 8 texts of ≤ 32 characters, `truncated`), drawn by the web as canvas / SVG elements, never injected as markup. The gallery is not in `counts` (revision lists stay small); it is served by its own route.
- **The PM's choice belongs to the Secondary CAD file, in an append-only table** (`cad_file_box_type_choices`: shape, `work_order_item_id` or null = cleared, who / when; never updated or deleted; the latest row per shape is in force; ≤ 1,000 in force, ≤ 4,000 rows per file) and is **frozen on the revision at creation** (`design_revisions.box_types` = `FrozenBoxTypes`: choice id, shape, line id and a snapshot of the line's code, description and label), like ADR-042's answer and marks. Not a mapping section, because: the choice references another module's rows (work-order lines) that can be removed later, so it is validated at write against the work-orders module's exported service and again at publish — not a free document the web re-saves whole; quantities depend on it, so each choice keeps its own author, time and event; the gallery only exists after a build, while the mapping is edited before one, and a choice must not bump the mapping version (control points, GPS proposals and the rebuild flow key on it). A later choice needs «طبّق وابنِ من جديد» (`boxTypesChangedSince` tells the web), as corrections.
- **Validation at write** (`POST …/cad-files/:f/box-types`, `design:write`): the file is a Secondary (`NOT_SECONDARY_DRAWING`; also a DB trigger), current (`FILE_SUPERSEDED`), has a built revision with a gallery (`NOT_BUILT`); every shape is in the gallery of the file's latest draft or published revision (`SHAPE_NOT_FOUND`, 422); the project has a work order (`NO_WORK_ORDER`) and every line is a line of **this project's** work order (`LINE_NOT_IN_WORK_ORDER`, 422; also a DB trigger joining `work_order_items` → `work_orders.project_id`). No FK to `work_order_items`: a line may still be removed in the work-orders module (ADR-028); that case is caught by the check below. Any line of the work order may be chosen (no list of "box items" exists; none is invented); one line may serve several shapes. A choice equal to the one in force writes nothing.
- **Check** (`evaluateBoxTypes`, pure, used by readiness, publish and part H) on the revision's gallery and frozen choices against the work order's lines **now**. Applies to a Secondary in roles mode (`boxTypesApply`). Issues, all blocking: `WORK_ORDER_MISSING`, `BOX_SHAPES_NOT_READ` (no gallery: rebuild), `BOX_SHAPE_UNKNOWN` (boxes without a signature: reprocess the file, then rebuild), `BOX_SHAPES_TOO_MANY` (more than 200 shapes: unify the symbols in AutoCAD), `BOX_TYPE_UNSET` (one per shape with boxes and no choice — the owner's «shape with no type»), `BOX_TYPE_LINE_MISSING` (the chosen line is no longer in the work order). A choice for a shape absent from the drawing is ignored. These are **not drawing problems** (`DRAWING_PROBLEM_CODES`): the drawing is not wrong, a PM decision is missing, and a line removed after the build can only be seen by the API at readiness / publish, while drawing problems are frozen at build. They are shown on the problems page in their own section «أنواع البوكسات» next to the drawing problems, each with «اختر البند» (opens the gallery at that shape) and «اعرض على الرسمة» (zooms to a sample box).
- **Publish:** check key `box_types` (Secondary roles mode: issue count; General / legacy: ok, count null; `other_drawing` on the General also needs the Secondary's box types clear) and blocker `BOX_TYPES_UNCLEAR` {drawingKind `secondary`, issueCount, issues} after the drawing's own `PROBLEMS_OPEN` (and the General's `INSTALLATION_UNCLEAR`), before `CABINETS_MISMATCH`; `PublishReadiness.boxTypes` carries the report.
- **On each box** (`attrs.reading`, worker, from the frozen choices): `shape` and `boxType` {workOrderLineId, code, label} (null when unset). **Totals for part H are derived** (`BoxTypesReport.totals`: boxes per work-order line with its shapes), only when the check is ok, from the published revision (immutable inputs).
- **The type text:** label = the line's description, whitespace collapsed, cut to 80 characters (`boxTypeLabel`); the code is shown apart, LTR. **Now:** «عارض الرسومات» draws the label (and code) next to every box at its `attrs.drawingAt` (ADR-042) as an overlay — the frozen type of the draft, or the live choice not yet built marked «لم يُبنَ بعد» (ADR-039 immediate preview); a box with no type shows «بدون نوع» with an icon (not colour alone). The **As-Built DXF** (`cad.export_asbuilt`, ADR-030, the only DXF the program writes today) gets one MTEXT per box of the published Secondary on layer `BOX_TYPE` («code\Plabel», TrueType style so Arabic shows). **Deferred:** the corrected-drawing DXF of ADR-038 part 3 («نزّل الملف بالتصليحات») is not built; when it is, it writes the same `BOX_TYPE` texts.
- **API:** `GET …/cad-files/:f/box-types` (`cad_files:read` → `BoxTypeState`: in force, history, the previous version's choices), `POST …/cad-files/:f/box-types` (`design:write`, `SetBoxTypesRequest` → `BoxTypeState`; refusals `BOX_TYPE_WRITE_REFUSALS`), `GET …/design-revisions/:r/box-types` (`design:read` → `BoxTypesReport` with gallery, frozen choices, issues, totals, `changedSinceBuild`). The line picker uses the existing work-order read. Revision create / rebuild freeze the choices in the same transaction as the corrections and the installation.
- **New version of a Secondary** (ADR-038): choices are **not** carried over automatically; `BoxTypeState.previousVersion` offers them and «استخدم اختيارات النسخة السابقة» writes them as new rows (`fromPreviousVersion`) — only shapes present in the new gallery.
- **Events:** `box_type_choice.chosen` per row written {cadFileId, shape, workOrderLineId (null = cleared), previousWorkOrderLineId, fromPreviousVersion}. The worker's gallery is part of `design_revision.built`.
- **Web:** on the Secondary's draft page, a section «أنواع البوكسات»: a card per shape (picture, count, block names, «اعرض على الرسمة») with a work-order line picker (code LTR + description) and save; a rebuild notice when the live choices differ from the draft; the checklist row `box_types`; the label overlay on the canvas.
**Database:** migration `0023_box_types.sql`: `cad_inserts.shape_signature` (format check); `cad_file_shapes` (import output, replaced with the extraction on reprocess); `cad_file_box_type_choices` (append-only, Secondary-only and same-project-line triggers); `design_revisions.box_shapes` (build output) and `design_revisions.box_types` (frozen input, added to the frozen-inputs guard), both Secondary only.
**Golden run (Al-Fath Secondary, local fixtures):** 197 boxes → 1 shape (`box c`), count 197; before a choice 1 `BOX_TYPE_UNSET`; after one choice and a rebuild 0 issues and totals {line: 197}. A synthetic DXF test: the same geometry under two block names → 1 shape; the block rotated 90° and scaled ×2 → same shape; mirrored → 2 shapes; a box added on the page → `none`.
**Open questions (owner; the cautious reading is used meanwhile):**
1. Do two symbols that look the same but have different colours count as one type? (Now: yes — colour is not part of the shape.)
2. The text next to each box: the line's description (cut to 80 characters) with its code, or a short name typed by the PM? (Now: description + code.)
3. May any work-order line be chosen, or only some (e.g. items counted per piece)? (Now: any line of the work order.)
4. A new version of the Secondary: reuse the previous version's choices automatically? (Now: offered, applied only on the PM's click.)
5. After publishing, may a work-order line chosen for a box type be removed? (Now: not blocked; part H decides; before publishing it is `BOX_TYPE_LINE_MISSING`.)
6. Boxes in the General (if any are drawn there): typed too? (Now: no — box types are a Secondary reading, ADR-040.)
**Owner decision and review fixes (2026-11-12):** a Secondary mapped without text roles (legacy reading) is not exempt: `box_types` applies and gives the single blocking issue `READING_ROLES_MISSING` (owner: anything unclear is an error). The worker bounds symbol explosion (per-symbol and per-drawing entity budgets shared by shape and drawn centre; past them the symbol has no shape and its insertion point is used) and keeps only signatures in a bounded cache, a preview per new signature.
**Consequences:** shared contracts (this change): `box-types.schemas.ts`, `BoxReading.shape` / `boxType`, revision detail `boxTypes`, check key `box_types`, blocker `BOX_TYPES_UNCLEAR`, readiness `boxTypes`, event `box_type_choice.chosen`. Worker: signatures and previews at import, gallery and readings at build, `BOX_TYPE` texts in the As-Built DXF. API: box-types use cases and routes in the `cad` module (work-order lines through the work-orders module's exported service), freezing on create / rebuild, readiness and publish. Web: the gallery and picker, the checklist row and the problems-page section, the canvas labels; i18n ar/en/fr. Next ADR: 044, next migration: 0024.
